One release. Many systems. One tool.

Say a single release must touch an operational PostgreSQL database, a BigQuery data warehouse, a Bigtable key-value store, and a Kafka topic whose configuration must be in place before the first message arrives — with the guarantee that all of it lands in the right sequence.

Database migration tools are excellent at managing database changes. When a release spans different platforms and services, teams often coordinate the work with pipelines, scripts, and runbooks. It tales considerable effort to plan and implement.

TotalSchema is designed for exactly that gap. Changes in one place. One tool. All systems updated, in the order you define.

What it manages

Changes across your data platform

Manage relational databases and cloud data warehouses through JDBC, use dedicated connectors for selected cloud services, and extend coverage with scripts or custom connectors.

Features

Everything a data engineering team needs

A focused, production-ready feature set—no bloat.

Sequenced Cross-System Changes

Each change targets one system and has a defined position in the global execution order—so multi-system releases always run in exactly the sequence you intend.

State Tracking

A persistent state table records every applied change, with optional content hashing to detect tampering.

Multiple Script Types

SQL, Python, Shell, Groovy, and any JVM ScriptEngine scripting language your team already knows.

Flexible Execution Modes

Run once, run always, run on content change, or revert—each script declares its own lifecycle.

Environment Management

Separate configurations, variables, and system targets for DEV, QA, PROD, and any custom environment.

Variable Substitution

Powerful variable system with environment overrides, expression evaluation, and encrypted secret support.

Distributed Locking

Optional database-backed locking prevents concurrent executions across your team or CI/CD pipeline.

Wildcard Selection

Deploy an arbitrary subset of changes—no forced linear versioning. You decide what runs and when.

Validation

Built-in detection of change scripts that were modified after being applied—safeguarding deployment integrity.

Failure handling

Know what completed—and choose how to recover

Completed changes are recorded in the state table. By default, if an apply script fails, TotalSchema stops the change process; completed work stays recorded so you can review it and continue the remaining changes.

Optional automatic revert: You can request that TotalSchema revert completed changes when an apply error occurs. Write a corresponding revert script for each apply script so completed work can be undone.

Protect the state database: Back it up with your operational data. If it is lost, restore it or reconcile the recorded state against the target systems before running changes again.

How it fits

Already using Liquibase or Flyway? Keep them.

Liquibase and Flyway are proven tools for database migrations. Liquibase also supports some NoSQL databases through extensions, and its Flow Files can sequence commands. These tools keep migration history with the databases they manage; teams can coordinate wider releases through pipelines or other orchestration.

Aspect Liquibase / Flyway TotalSchema
Primary focus Managing migrations for a database Coordinating changes across systems in a release
Ordering Within a database; broader workflows can be coordinated externally or with flow features One defined execution order across change files and systems
Change history Migration history associated with the database being managed Completed changes recorded in a state table
Other systems Often coordinated externally, including with scripts and surrounding tooling Provided connectors, shell scripts, and user-developed connectors

If your changes affect one database, you may not need TotalSchema. Keep Liquibase or Flyway for the databases they already manage well, and use TotalSchema where a release needs cross-system coordination.
